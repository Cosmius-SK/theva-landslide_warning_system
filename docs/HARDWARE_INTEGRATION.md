# ESP32 telemetry integration

## Scope and status

The integration supports a simulated telemetry test feed from the ESP32-S3 DevKitC-1 N16R8. The three readings are generated by firmware and are **SIMULATED TEST ONLY**; potentiometers have not arrived and are not part of this phase. This feed appears separately from the risk model, operator connection and virtual controls. Existing risk thresholds and fallback behavior are unchanged.

The software endpoint, display panel and firmware source are implemented in this branch. This does not mean the Preview API is deployed or that physical end-to-end integration has succeeded. Success requires an actual ESP32 packet to be accepted by Preview and visible with a matching sequence/readings on `/display`.

## Packet contract

`POST /api/telemetry` accepts this JSON shape over HTTPS:

```json
{
  "deviceId": "theva-esp32-01",
  "sequence": 4,
  "sentAt": "2026-11-23T10:00:00Z",
  "label": "SIMULATED TEST ONLY",
  "readings": {
    "moisture": 58,
    "rainfall": 42,
    "movement": 3
  }
}
```

The firmware authenticates with `Authorization: Bearer <device token>`. The ID must match the server-side `TELEMETRY_DEVICE_ID`; the token is configured server-side as `TELEMETRY_DEVICE_TOKEN` and locally in an ignored `secrets.h`. The Supabase service-role key and operator credential are never sent to the device.

The endpoint accepts only the exact `SIMULATED TEST ONLY` label, a matching device ID, a positive safe integer sequence, UTC timestamp no more than 30 seconds old or 60 seconds in the future, and exactly three integer values from 0 through 100. The Preview database's ingestion RPC atomically accepts only a greater sequence for that device. Duplicate or older sequence numbers return HTTP 409 with the latest accepted sequence. The endpoint returns only that configured device's readings to dashboard clients.

## Preview persistence and dashboard

The selected Preview Supabase project is `qgmvlsgzpvqabiupmnki` (`theva-live-preview`). Inspection found `public.device_telemetry` with RLS enabled and an `ingest_device_telemetry` function. The function stores only the latest sequence/readings for the device and updates only when the sequence increases. Direct table access and function execution are restricted to `service_role` and the database owner; the browser and ESP32 have neither access.

`GET /api/telemetry` returns the configured device's latest row and computes online status from `received_at` with a 45-second heartbeat window. `/display` and Diagnostics show device online/offline state, last seen, sequence and the labelled values. Device status is separate from operator connection/cloud status. Device readings are not inputs to the risk model during this simulated-test phase.

## Firmware, setup and verification

The firmware lives in `firmware/esp32_simulated_telemetry/`. It connects over Wi-Fi, synchronizes UTC, validates the Preview TLS root certificate, generates labelled readings, increments and persists its sequence in NVS, and retries using capped exponential backoff. See [ESP32 setup and verification](ESP32_TELEMETRY_SETUP.md) for Preview-only configuration, flashing, Serial Monitor and the physical packet verification procedure.

Automated endpoint and dashboard tests use in-memory Supabase doubles. They do not validate Preview persistence, a Vercel deployment, TLS configuration, or a physical packet. Do not claim physical integration success until the final procedure observes a packet from the actual ESP32 on the Preview dashboard and verifies the matching Preview row.
